# Deployment, storage and accounts

What GitHub holds, what a running LEARNABLE needs besides it, where uploads live, and how
accounts keep material private. Written 2026-09-25 from the repository as it is, not from
plans. **No hosted deployment exists yet**: everything below about hosting is what the code
supports and what must be provisioned, not something that has been verified in production.

## 1. Is everything needed to build and run LEARNABLE in GitHub?

**All the code and reproducible configuration: yes. The running services, secrets and data: no,
by design.**

| | In GitHub | Where |
|---|---|---|
| **A. Code and reproducible configuration** | yes | backend (`backend/app`), web (`web/src`), iOS (`ios/`, project generated by XcodeGen from `ios/project.yml`) |
| | yes | dependencies pinned: `backend/requirements.lock` + `requirements-dev.lock`, `web/package-lock.json` |
| | yes | database schema: SQLAlchemy models + Alembic migrations (`backend/migrations`), checked against each other in CI |
| | yes | build/start: `backend/Dockerfile`, `docker-compose.yml` (Postgres + API), `web` `npm run build`, CI workflows in `.github/workflows` |
| | yes | environment template: `.env.example` (every setting, no values) |
| | n/a | no worker/queue service: background jobs (document processing, AI generation) run in the API process; interrupted ones are recovered at startup (`app/services/recovery.py`) |
| **B. Services to run it** | no | PostgreSQL 16 (pgvector image in compose); a host for the API container; a static host or reverse proxy for `web/dist` on the same origin as `/api`; durable file storage (§3); optionally an AI provider |
| **C. Secrets** | no | `AUTH_SECRET`, AI keys, storage keys (§2), set in each environment |
| **D. Runtime data** | no | users, courses, answers and XP (database); uploaded files (storage). Never committed (`.gitignore` covers `.env*`, `*.db`, `backend/var/`) |

A fresh clone plus a database, `AUTH_SECRET` and a storage location runs the whole app with the
mock AI (`AI_PROVIDER=mock`); `docker compose up --build` does exactly that locally.

## 2. Secrets: GitHub Actions vs the runtime environment

GitHub secrets do **not** reach a running server. They exist only inside workflow runs.

| Secret | GitHub Actions secret | Runtime environment (the host running the API) |
|---|---|---|
| `AUTH_SECRET` (≥32 random chars) | not needed (CI uses throwaway test values) | **required** |
| `DATABASE_URL` | not needed | **required** (Postgres) |
| AI keys: `GROQ_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, `MISTRAL_API_KEY`, `NVIDIA_API_KEY`, `CLOUDFLARE_API_TOKEN`, `COHERE_API_KEY`, `DASHSCOPE_API_KEY`, `TENCENT_TOKENHUB_API_KEY`, `SILICONFLOW_API_KEY` | only for the manual `real-ai.yml` validation workflow | as `AI_API_KEY` (single provider) or `AI_<PROVIDER>_API_KEY` (router), for real AI features |
| Storage: `STORAGE_ACCESS_KEY_ID`, `STORAGE_SECRET_ACCESS_KEY` | not needed | required when `STORAGE_BACKEND=s3` |
| Email: `SMTP_USERNAME`, `SMTP_PASSWORD` (with `EMAIL_BACKEND=smtp`, `SMTP_HOST`, `SMTP_FROM`, `PUBLIC_APP_URL`) | not needed | required for "Forgot your password?" emails to be delivered |

Rules: never commit values; never put a server secret in a `LEARNABLE_PUBLIC_*` web variable
(the web build's `check:secrets` fails if one appears in the bundle); rotate `AUTH_SECRET` to
sign everyone out.

## 3. Uploaded documents: where exactly they live

```
POST /courses/{id}/documents  (ownership checked, type detected from content, size limit)
  → original bytes   → DocumentStorage under key  courses/{course_id}/documents/{document_id}
  → metadata         → `documents` row (course, chapter, filename as display text only, sha256,
                       status, purpose, page count …)
  → extraction (background) → cleaned passages in `document_chunks` (text, page range, section)
  → curriculum / question-bank import → Concepts and Learning Items linked to their passages
                       (`concept_sources`, `learning_item_sources`) → "View source"
```

- **Original bytes:** `STORAGE_BACKEND=local` writes them under `STORAGE_LOCAL_DIR` (default
  `backend/var/documents`), written to a temporary file then renamed, so a crash never leaves
  a truncated file. A failed write leaves no temporary file behind. `STORAGE_BACKEND=s3` puts
  them in a **private** bucket on any S3-compatible service (AWS S3, Cloudflare R2, Backblaze B2,
  MinIO: `STORAGE_ENDPOINT`, `STORAGE_BUCKET`, `STORAGE_REGION`, `STORAGE_PREFIX`, keys above).
- **Keys** are built only from server-generated ids, never from the user's filename.
- **Extracted text and metadata:** in the database (PostgreSQL in production), not in storage.
- **Retrieval:** `GET /documents/{id}/file` streams the original after the ownership check (404
  for anyone else), always as an attachment with `nosniff` and `no-store`. There are no public
  URLs and no pre-signed links: every download passes the API's check.
- **Deletion:** deleting a document removes its row, its passages and then its file (a crash in
  between leaves an orphan file, never a row pointing at nothing). Concepts that lose their last
  source are kept and flagged `needs_source_review`. Deleting a course deletes all of its files.
- **Failures:** an unreadable file is kept with status `FAILED` and a user-safe reason. A row
  whose file has gone missing answers `404 file_missing` on download instead of a server error.

**Do they survive restarts and redeployments?**

| Setup | Restart | Redeploy / new container |
|---|---|---|
| `local` on the container's own disk | yes | **no**: files are lost while their rows survive (broken sources) |
| `local` on a persistent volume (`docker-compose.yml` mounts `documents_data`) | yes | yes, as long as the volume is kept |
| `s3` | yes | yes |
| Database (Postgres volume or managed Postgres) | yes | yes |

For hosting, use `STORAGE_BACKEND=s3` (or a persistent volume) and managed/volume-backed
Postgres, and back both up together.

## 4. Accounts and privacy

- Anyone can register (`POST /auth/register`, email + 12-character password, Argon2id). Login
  returns a signed access token (60 minutes); the user id inside it is the only identity the API
  trusts, never an id sent by the client.
- Every course-scoped query filters by the authenticated user's course (the course row carries
  `user_id`; children carry `course_id`). Another user's resource answers **404, never 403**, so
  ids can't be probed. This covers courses and their hierarchy, documents and downloads,
  passages, learning items and questions, AI jobs and proposals, sessions, answers,
  evaluations, overrides, hints, consolidation, progress, the dashboard, XP, streaks, goals and
  activity.
- **Evidence:** `backend/tests/test_isolation.py` runs every course-scoped endpoint as an
  intruder and checks 404 and unchanged data. `test_dashboard.py` checks that a second account
  sees no courses, XP, goal or activity of the first. The Playwright run registers a second
  account in the browser, checks it sees none of the demo account's material, checks that its
  direct API requests for the demo course, summary, outline and file answer 404, and switches
  accounts in the same tab without showing cached data.
- **Passwords** are stored only as Argon2id hashes: nobody can read one back, on GitHub or in the
  database. "Forgot your password?" emails a single-use, 30-minute link; any password change ends
  every session of the account (token version). `scripts/set_password.py` sets a new password
  administratively.
- **Sign-out** clears the token, the whole query cache and saved answer drafts. Signing in clears
  the cache again (e.g. after an expired session). Logout is client-side (stateless tokens):
  a copied token stays valid until it expires; rotating `AUTH_SECRET` revokes all of them.

## 5. What still has to be provisioned

1. A PostgreSQL database and its `DATABASE_URL`, with backups.
2. A host for the API container: run `alembic upgrade head` as a deploy step, then the image.
3. Durable storage: an S3-compatible bucket (private) with its credentials, or a persistent
   volume.
4. Serving `web/dist` on the same origin as `/api` (reverse proxy), over HTTPS.
5. `AUTH_SECRET` and the rest of `.env.example` in the host's environment.
6. An email provider for password resets (`EMAIL_BACKEND=smtp` + SMTP settings), and
   `PUBLIC_APP_URL` set to the public web address. Without it, reset emails only reach the log.
7. For real AI: a provider key in the runtime environment (not only in GitHub), then the
   validation in docs/FREE_AI_ROUTING.md.
